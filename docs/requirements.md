# Chatterbox MVP Requirements

Status: Draft for review · Source of truth for scope. Changes to scope need a written proposal (value, cost, risk, schedule impact).

## 1. Purpose
Chatterbox is a lightweight social feed. Visitors can read a shared feed. Registered users can log in and publish short text posts.

## 2. Definitions
| Term | Meaning |
|---|---|
| Visitor | Anyone not logged in |
| User | A registered, logged-in account |
| Public identifier | The **username**, shown on posts |
| Feed | All posts, newest first |

## 3. Decisions (fixed for the MVP)
| ID | Decision |
|---|---|
| D1 | Registration fields: email, username, password |
| D2 | Username: 3–30 characters, `A–Z a–z 0–9 _`, unique ignoring case |
| D3 | Password: 12–128 characters, no composition rules |
| D4 | Post content: 1–280 characters after trimming whitespace |
| D5 | Feed returns the newest 100 posts; no pagination in the MVP |

## 4. Functional requirements

### FR-01 Account registration
- **FR-01.1** A visitor shall be able to register with email, username and password.
- **FR-01.2** The server shall validate every field (format, length, required) regardless of client checks.
- **FR-01.3** Email and username shall each be unique (case-insensitive); a duplicate shall be rejected with a clear, non-sensitive error.
- **FR-01.4** Passwords shall be hashed with Argon2id before storage; plaintext passwords shall never be stored or logged.
- **FR-01.5** Responses shall never include the password hash or other sensitive fields.
- **FR-01.6** Invalid input shall return field-level validation errors in the documented error format.

### FR-02 Login
- **FR-02.1** A registered user shall be able to log in with email and password.
- **FR-02.2** A successful login shall create a server-side session and set a secure, HTTP-only cookie.
- **FR-02.3** The session identifier shall be regenerated on login.
- **FR-02.4** A failed login shall return the same generic error whether or not the email exists.

### FR-03 Logout
- **FR-03.1** A logged-in user shall be able to log out.
- **FR-03.2** Logout shall destroy the server-side session and clear the cookie.
- **FR-03.3** A session destroyed by logout shall not authorise any protected endpoint.

### FR-04 View feed
- **FR-04.1** Any visitor or user shall be able to view the feed without logging in.
- **FR-04.2** The feed shall contain posts from all users, ordered by creation time, newest first.
- **FR-04.3** Each post shall show the author's username, the content and the creation date/time.
- **FR-04.4** The UI shall show an empty state when there are no posts.
- **FR-04.5** The UI shall show a loading state while fetching and a clear error state on API or network failure.
- **FR-04.6** The feed shall return at most the newest 100 posts (D5).

### FR-05 Create post
- **FR-05.1** Only a logged-in user shall be able to create a post; unauthenticated requests shall be rejected.
- **FR-05.2** The server shall validate post content: reject empty or whitespace-only content and content over 280 characters (D4).
- **FR-05.3** Each post shall be associated with the authenticated user, never with a client-supplied author.
- **FR-05.4** The creation timestamp shall be generated by the server.
- **FR-05.5** The response shall indicate success (with the created post) or a specific, non-sensitive failure.
- **FR-05.6** After creating a post, the UI shall show it in the feed.

### FR-06 Persistence
- **FR-06.1** Users and posts shall be stored in PostgreSQL.
- **FR-06.2** The schema shall be managed by version-controlled migrations.
- **FR-06.3** Data shall survive container restarts while the database volume is retained.
- **FR-06.4** Documentation shall distinguish restarting containers from deleting the volume, and warn that deleting the volume deletes data.
- **FR-06.5** Persistence shall be claimed only after it has been verified (S7-1).

## 5. Non-functional requirements

### Security
- **NFR-S1** Untrusted input shall be validated on the server.
- **NFR-S2** Authenticated endpoints shall reject unauthenticated requests.
- **NFR-S3** Secrets shall never be committed; configuration shall come from environment variables, with `.env.example` containing placeholders only.
- **NFR-S4** Errors shall not expose stack traces, SQL or other internal details.
- **NFR-S5** Cookie, CORS and CSRF protections shall match the documented strategy (S1-4).
- **NFR-S6** Database access shall use parameterised queries via the ORM.

### Maintainability
- **NFR-M1** TypeScript shall be used in both apps; lint and format checks shall pass.
- **NFR-M2** Significant technical decisions shall be recorded as ADRs.

### Testability
- **NFR-T1** Unit, integration, frontend and end-to-end tests shall exist for the main journeys.
- **NFR-T2** Tests shall be repeatable, with isolated state and no dependence on personal databases or credentials.

### Portability
- **NFR-P1** The full stack shall run locally via Docker Compose from documented commands.
- **NFR-P2** All configuration shall come from environment variables.

### Reliability
- **NFR-R1** The API shall expose a health check that reports database connectivity.
- **NFR-R2** Services shall wait for database readiness before serving traffic.
- **NFR-R3** Migrations and persistence shall be verified as part of release testing.

## 6. In scope
Registration, login/logout, shared feed, text posts, author and date display, PostgreSQL persistence, Docker-based local run, automated tests, GitHub Actions CI, project documentation.

## 7. Out of scope (needs an approved new requirement)
Likes and reactions, comments, direct messages, image/video upload, follow relationships, notifications, recommendations, advanced roles, real-time updates, mobile apps, microservices, production cloud deployment.

## 8. Known limitations
- The feed shows only the newest 100 posts (D5).
- No password reset and no email verification.
- Posts cannot be edited or deleted.
- No rate limiting beyond what is documented in S1-4.

## 9. Traceability
Each requirement ID maps to at least one acceptance test in S1-6 (issue #7). Requirements without a test are defects in this document.
